Apontamento JERP — Inspeção e Embalagem

Sistema: gde-insp-embalagem Data: 07/07/2026 Versão do código: implementação atual em src/
Resumo: O apontamento de produção no JERP ocorre uma vez por caixa embalada, após a inspeção visual de todos os blisters. A modificação recente inclui o array embalagens no payload, com um objeto { barcode } por blister embalado — código QR lido na inspeção. A quantidade oficial vem sempre do banco local, nunca do frontend.

1. Visão geral do ciclo

O sistema controla inspeção visual de caixas, blisters e peças (via worker de visão) e, ao final de cada caixa, realiza o apontamento de produção no JERP — único momento em que dados de produção são escritos no ERP.

Sincronizar OP (JERP → local) → Inspecionar caixa / blisters / peças → Persistir no PostgreSQL (packedAt + code QR) → Apontar no JERP (local → JERP) com embalagens[].barcode → Salvar idBarras na caixa → Imprimir etiqueta (pdfBase64) → Próxima caixa

O apontamento não acontece a cada blister. Ocorre quando a inspeção da caixa termina e a etiqueta é solicitada.

2. Integrações com o JERP

2.1 Leitura GET

Usadas para sincronizar OP, validar quantidades e reconciliar pendências. Nenhum dado de produção é enviado.

3. Preparação da OP (antes da inspeção)

Ao abrir /op/{opId}, o sistema chama syncAndGetOpToProduceById:

  1. Consulta OP no JERP (getOpFromRef)
  2. Se OP não existe localmente: valida (validateOpJerpToProduce), seleciona embalagens (selectOpPackagings), cria ProductType, BoxType, BlisterType, Op, OpBox e OpBoxBlister
  3. Planeja caixas a partir de quantidadeAProduzir do JERP
  4. Se não há caixas pendentes: reconcilia quantidade local com JERP

3.1 Fórmulas de planejamento

blisters totais  = ceil(quantidadeAProduzir / slots)
caixas totais    = ceil(blisters / limitPerBox)
última caixa     = pode ter menos blisters; último blister pode ter menos peças

Exemplo: 1.080 peças, 6 slots, 8 blisters/caixa → 180 blisters → 23 caixas (última com 4 blisters × 6 = 24 peças).

3.2 Reconciliação de quantidade

quantityToProduce (local) = peças já embaladas (banco) + quantidadeAProduzir (JERP)

4. Fluxo de inspeção por caixa

Tela: src/app/op/[opId]/page.tsx — 4 etapas (step):

4.1 Finalização da caixa (gatilho do apontamento)

Quando todos os blisters da caixa foram inspecionados:

  1. persistBoxStatusWithBlisters(boxId, blisters) grava:
    • OpBoxBlister.packedAt e OpBoxBlister.code (QR real)
    • OpBox.packedAt e OpBox.status = PACKAGED
  2. Após 2 segundos: printTag(boxId) → POST /api/op-jerp/barcode

Até este ponto nada foi enviado ao JERP. Toda inspeção fica no banco local e no worker de visão.

4.2 Sequência do apontamento (fluxo normal)

Operador finaliza último blister da caixa → persistBoxStatusWithBlisters (PostgreSQL) → printTag (frontend) → fetchAuthoritativePackedBoxSummary (server action) → POST /api/op-jerp/barcode → getAuthoritativeBoxPackedSummary (banco) → buildJerpEmbalagemApontamento (monta embalagens[]) → generateBarcode → POST JERP /ordemproducao → saveTagId (OpBox.barCode) → OpActivityLog (auditoria) → Diálogo de impressão (idBarras + pdfBase64)

5. Apontamento — payload e códigos de barra

5.1 Modificação principal: array embalagens

Antes, o payload enviava apenas id, quantidadeApontada e userName. Agora inclui embalagens: um item por blister embalado, cada um com o código QR lido na inspeção.

{
  "id": 430505,
  "quantidadeApontada": 48,
  "userName": "operador@gde.com.br",
  "embalagens": [
    { "barcode": "0710380009" },
    { "barcode": "0710380006" },
    { "barcode": "0710380005" }
  ]
}

5.2 Montagem do payload

Função central: buildJerpEmbalagemApontamento() em build-jerp-embalagem-apontamento.ts

blisters.map((blister) => ({ barcode: blister.code }))
  • Origem do barcode: OpBoxBlister.code — QR lido na etapa 1 da inspeção
  • Ordem: packedAt ASC (ordem de embalagem)
  • Quantidade por blister: usada apenas para calcular quantidadeApontada; não vai no payload JERP
  • Filtro: apenas blisters com packedAt IS NOT NULL

5.5 Resposta do JERP (PrintTagJerpDto)

{
  "message": "...",
  "id": 430505,
  "quantidadeApontada": 48,
  "idBarras": 7285300651,
  "quantidadePendente": 1032,
  "descricao": "TL-06-2-0007_02",
  "pdfBase64": "<PDF da etiqueta em Base64>"
}

Após sucesso: saveTagId grava OpBox.barCode e OpBox.barCodeGeneratedAt.

5.6 Fonte autoritativa dos dados

A quantidade e lista de blisters nunca vêm do cliente para o apontamento:

getAuthoritativeBoxPackedSummary(boxId)
  → getPackedBlistersByBox(boxId)   // WHERE packedAt IS NOT NULL
  → quantity = soma(blister.quantity)

O campo clientQuantity enviado pela UI serve apenas para detectar divergência cliente × banco. Se divergir, usa o banco e registra alerta no log.

9. Fluxos especiais

9.1 Quebra de caixa (PACKAGED_W_BREAK)

Supervisor autoriza finalizar caixa antes de preencher todos os blisters planejados. Remove blisters não embalados, persiste os embalados, marca PACKAGED_W_BREAK e gera etiqueta normalmente — apontamento contém somente blisters efetivamente embalados.

9.2 Reimpressão de etiqueta

Pelo painel diário (generateBarcodeByBoxId): reutiliza generateBarcode() com dados do banco. Não passa pela rota /api/op-jerp/barcode (sem auditoria automática). Pode gerar novo apontamento no JERP se chamado novamente.

9.3 Conclusão da OP

opCompletionNowHandler verifica localmente: todas OpBox com packedAt e barCodeGeneratedAt preenchidos → Op.status = COMPLETED. Não há chamada ao JERP para encerrar a OP.

11. Exemplo completo — OP 76691, caixa de 48 peças

Contexto: 8 blisters × 6 peças.

  1. Operador inspeciona caixa → blister 1 (QR 0710380009, 6 peças) → … → blister 8

    { "barcode": "0710380010" },
    { "barcode": "0710380007" },
    { "barcode": "0710380008" },

    { "barcode": "0710380003" }

  1. JERP responde com idBarras, quantidadePendente: 1032, pdfBase64
  2. Sistema salva barCode na caixa e imprime etiqueta
