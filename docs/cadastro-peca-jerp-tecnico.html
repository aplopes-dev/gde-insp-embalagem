Cadastro de Peças — Integração GDE × JERP

Sistema: gde-insp-embalagem Assunto: Fluxo, payloads e requisitos para automatização Data: 17/07/2026 Versão: 1.1
Em resumo: “Cadastro de peça” no GDE é o registro de dados mestres de embalagem (produto, blister e caixa) na abertura de uma OP nova. Produto e caixa já são criados sozinhos. O que falta para automação plena é o JERP enviar sempre slots e limitePorCaixa na embalagem blister. Sem isso, a linha depende do diálogo de supervisão.

1. O que é o cadastro de peça

Não é o registro de cada peça física inspecionada. É o cadastro local necessário para executar uma OP nova:

ConceitoEntidade GDEOrigem JERPFunção
Peça / Produto ProductType produto Item a embalar (ID = ID JERP)
Blister / Cartela BlisterType Embalagem com “blister” ou “cartela” no nome Define slots e limitPerBox
Caixa BoxType Embalagem com “caixa” ou “box” no nome Embalagem final; vinculada ao blister
Ordem de Produção Op + caixas/blisters OP do JERP Planejamento operacional
IDs locais = IDs do JERP. Códigos gerados pelo GDE: PROD_{id}, BLISTER_{id}, BOX_{id}. O GDE não escreve esses dados mestres de volta no JERP.

2. Fluxo atual

Operador abre /op/{id} → GET JERP /ordemproducaoid/{id} (fallback: /ordemproducao/{numero}) → Valida OP (id, número, produto, qtd > 0, ≥ 2 embalagens) → OP já existe local? SIM → carrega / reconcilia → inspeção NÃO → seleciona blister + caixa pelo nome → resolve slots e limitePorCaixa 1) banco local 2) campos JERP 3) histórico do produto → AUTO: cria ProductType, BoxType, BlisterType e Op → SUPERVISOR: diálogo (slots, limitPerBox, auth liderança)

Produto e caixa são sempre criados automaticamente a partir do JERP. O único bloqueio da automação é a capacidade do blister (slots / limitePorCaixa).

2.1 Prioridade de resolução

#FonteCondiçãoResultado
1local_dbBlister já existe no GDE com slots e limitPerBox > 0AUTO
2jerp_opJERP envia slots e limitePorCaixa > 0AUTO
3historyOP anterior do mesmo produto.id com blister válidoAUTO
4—Nenhuma das anterioresSUPERVISOR

Planejamento: peças por caixa = slots × limitPerBox. Blisters = ceil(quantidadeAProduzir / slots); caixas = ceil(blisters / limitPerBox).

4.2 Classificação de embalagens

TipoCritério no nomeExemplo
BlisterContém blister ou cartelaBLISTER-TL-06-2-0007_02
CaixaContém caixa ou boxCAIXA 520X320X170 TRIPLEX

Com vários blisters, o GDE escolhe o mais similar ao nome do produto. Nomes com “tampa” são penalizados. Se ambíguo, o supervisor pode selecionar.

5. O que o GDE grava localmente

ProductType  { id: produto.id, name, code: "PROD_{id}" }
BoxType      { id: caixa.id,   name, code: "BOX_{id}" }
BlisterType  { id: blister.id, name, code: "BLISTER_{id}",
               slots, limitPerBox, boxTypeId }
Op           { id, code: numero, FKs, quantityToProduce,
               OpBox / OpBoxBlister planejados }

Quando exige supervisor, a UI recebe requiresSupervisorConfig: true (sem gravar a OP). Após auth de liderança, o GDE cria tudo com os valores informados. 

// Entrada do diálogo (interno GDE — não vai ao JERP)

6. O que solicitar ao JERP

Pedido principal: a API de OP deve devolver, em cada embalagem blister/cartela, slots e limitePorCaixa como inteiros > 0, vindos do cadastro mestre de embalagens — de forma permanente e consistente.

6.1 Já necessário hoje

  1. OP com id, numero, quantidadeAProduzir > 0.
  2. produto.id (e preferencialmente produto.nome).
  3. ≥ 2 embalagens: uma blister/cartela e uma caixa/box identificáveis pelo nome.
  4. Cada embalagem com id, nome, quantidadeAlocada ≥ 1.

6.2 Necessário para auto-cadastro pleno

Campo JERPNo GDESignificadoExemplo
embalagens[].slotsBlisterType.slotsPeças por blister6
embalagens[].limitePorCaixaBlisterType.limitPerBoxBlisters por caixa8

6.3 Qualidade de dados (recomendado)

  • Nomes estáveis com BLISTER/CARTELA ou CAIXA/BOX explícitos.
  • Blister de produto distinguível de tampa/acessório.
  • Mesmo embalagem.id → mesma capacidade entre OPs (salvo mudança real).
  • Produto novo: sem esses campos, o diálogo de supervisão é inevitável.

6.4 Checklist de solicitação

#ItemPrioridade
1Expor slots (integer > 0) no blister da resposta da OPALTA
2Expor limitePorCaixa (integer > 0) no blister da resposta da OPALTA
3Preencher esses campos no cadastro mestre para todos os produtos ativosALTA
4Padronizar nomenclatura BLISTER/CARTELA e CAIXA/BOXMÉDIA
5Garantir IDs estáveis de produto e embalagensMÉDIA
6Documentar o contrato JSON da OP (tipos, obrigatoriedade, exemplos)MÉDIA

7. Limitações conhecidas

  1. Sem slots/limitePorCaixa e sem histórico → cadastro automático não completa.
  2. Valores do diálogo de supervisão ficam só no GDE; não sincronizam de volta ao JERP.
  3. Histórico pode reutilizar capacidade antiga se a embalagem mudar e o JERP não enviar os novos campos.
  4. Classificação blister/caixa depende do texto do nome; fora do padrão, falha a identificação.
  5. O módulo de visão (YOLO) não participa deste cadastro; classes visuais são treinadas à parte.

8. Resumo executivo

  • O cadastro ocorre na primeira abertura de uma OP inexistente no banco local.
  • Produto e caixa já são criados automaticamente a partir do JERP.
  • O blister precisa de capacidade: banco local → JERP → histórico → ou supervisão.
  • Para eliminar o diálogo em produtos novos, o JERP deve sempre enviar slots e limitePorCaixa nas embalagens de blister da API de OP.
